# Application Insights

## The plain-English version

Your app is a black box once it's deployed — you can't attach a debugger to a production App Service. Application Insights is **a flight recorder for your app**: it automatically captures every incoming HTTP request, every outgoing HTTP call, every exception, every SQL query, with timing, and ships it all to Azure where you can query it, graph it, and get alerted on it. You didn't write logging code for most of this — it's collected by intercepting things at the HTTP pipeline / `HttpClient` / ADO.NET level.

The core building blocks, in plain terms:

- **Requests** — every inbound HTTP call your app served, with duration and status code. This is how you'd notice "the `/api/orders` endpoint got slow starting Tuesday."
- **Dependencies** — every outbound call *your app made to something else* (a database, another API, Blob Storage, Service Bus). This is how you'd notice "we're slow because Service Bus is slow," not "we're slow, full stop."
- **Exceptions** — every unhandled (and, if you log them, handled) exception, with the full stack trace, correlated to the request that caused it.
- **Custom events/metrics** — anything you explicitly want to track that isn't automatic ("user clicked checkout," "queue depth is 400").
- **Traces** — your own `ILogger` log lines, shipped to the same place, so a log line and the request that produced it show up together instead of being two separate things you have to correlate by timestamp.

## The analogy that makes it click

Think of a request coming into your API as a relay race with a baton. Application Insights tapes a tiny tracking chip to the baton (this is literally what a "correlation ID"/"operation ID" is) before the race starts. Every leg of the race — your controller, the SQL call, the Blob Storage call, the Service Bus publish — reports back "I had the baton from this time to this time." At the end, Application Insights can show you the *entire race*, leg by leg, for one specific request — which is exactly what "Application Map" and the end-to-end transaction view in the Azure Portal look like.

## How this repo implements it

**`src/WebApp/Program.cs`**:
```csharp
var appInsightsConnectionString = builder.Configuration["ApplicationInsights:ConnectionString"];
if (!string.IsNullOrWhiteSpace(appInsightsConnectionString))
{
    builder.Services.AddApplicationInsightsTelemetry();
}
```
One line normally — `AddApplicationInsightsTelemetry()` — but it's wrapped in a null check here for a reason worth remembering (see below). It reads the connection string from `ApplicationInsights:ConnectionString` or the `APPLICATIONINSIGHTS_CONNECTION_STRING` environment variable — the latter is what App Service sets **automatically** the moment you link an Application Insights resource to the App Service in the Azure Portal. Nothing else in the app needs to change.

The Functions project gets the same telemetry for free, differently: `src/Functions/Program.cs` (generated by the Functions template, untouched) wires up `OpenTelemetry` + `Azure.Monitor.OpenTelemetry.Exporter` conditionally on the same environment variable being present — Functions uses OpenTelemetry as the underlying pipe to Application Insights rather than the classic SDK, which is the direction Microsoft has been moving the whole ecosystem (Application Insights classic SDK is in maintenance mode; OpenTelemetry is the future path for both).

## The bug this repo actually hit — worth remembering on its own

`AddApplicationInsightsTelemetry()` does **not** gracefully do nothing when there's no connection string configured. It throws `InvalidOperationException: A connection string was not found` **at startup**, crashing the whole app before it even binds to a port. This is the opposite of what most people assume ("it'll just no-op locally") and it's exactly what happened while building this repo — real error, not a hypothetical:
```
Unhandled exception. System.InvalidOperationException: A connection string was not found. Please set your connection string.
```
The fix is the `if (!string.IsNullOrWhiteSpace(...))` guard shown above — only register it when a real connection string exists. This is worth remembering precisely because it contradicts the reasonable-sounding assumption that "adding an SDK for something optional will just be a no-op if unconfigured."

## What's real vs. reference-only in this repo

The conditional wiring itself is verified — the app starts cleanly with no connection string configured (the whole point of the fix above), proving the guard works. Actually seeing telemetry show up in the Azure Portal requires a real Application Insights resource, which wasn't available in this environment.

## Interview Questions

**Q: What's the difference between a Request and a Dependency in Application Insights?**
A Request is something *called your app* (inbound). A Dependency is something *your app called* (outbound) — a database, another API, a queue, a storage account. Both get timed automatically; the distinction is which direction the arrow points.

**Q: How does Application Insights correlate a request with the SQL call and the exception it caused?**
Via an operation ID (and, more granularly, a parent/child span ID) attached to every telemetry item produced while handling a single request. Everything emitted during that request — the request itself, any dependency calls, any exceptions, any log traces — shares the same operation ID, which is what lets the Portal show you "this one request" as a single connected timeline instead of a pile of unrelated log lines.

**Q: What's sampling, and why would you turn it on?**
At high traffic volume, shipping *every single* telemetry item is expensive and mostly redundant — you don't need 10,000 identical "GET /health, 200, 3ms" entries to know that endpoint is healthy. Sampling ships a representative percentage of telemetry instead of all of it, cutting cost and ingestion volume while still catching the exceptions and outliers because Application Insights sampling is designed to preserve related items together (whole traces, not random single events) rather than sampling each telemetry type independently.

**Q: This app's code doesn't gracefully handle a missing connection string — why not just let the SDK "figure it out"?**
Because it doesn't — `AddApplicationInsightsTelemetry()` throws at startup with no connection string configured, which is the opposite of the reasonable assumption that an optional telemetry SDK would just quietly do nothing. Wrapping the call in `if (!string.IsNullOrWhiteSpace(connectionString))` is the actual fix, not a defensive style choice — the app crashes on launch without it.

**Q: How does App Service know which Application Insights resource to send telemetry to?**
When you link an Application Insights resource to an App Service in the Azure Portal (or via Bicep/ARM), Azure automatically sets the `APPLICATIONINSIGHTS_CONNECTION_STRING` application setting (an environment variable) on the App Service. The app never hardcodes which resource it talks to — that binding lives in Azure resource configuration, not in the code or in `appsettings.json`.

**Q: Classic Application Insights SDK vs. OpenTelemetry — which would you pick today?**
OpenTelemetry, for anything new. Microsoft has explicitly put the classic Application Insights SDK into maintenance mode and is standardizing on OpenTelemetry (a vendor-neutral instrumentation standard) with `Azure.Monitor.OpenTelemetry.Exporter` as the piece that ships that data specifically to Azure Monitor/Application Insights. The Functions project in this repo already uses that path; it's the direction the WebApp project would move too if this weren't a demo.
